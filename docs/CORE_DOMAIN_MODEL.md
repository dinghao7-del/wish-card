# 核心领域模型与主闭环

更新时间：2026-05-13

## 1. 为什么要统一模型

当前项目里已经有计划、AI 推荐、任务、习惯、奖励、引导页画像等能力，但它们分散在不同页面和文件中：

- `PlanWizard` 负责创建计划和日程模板。
- `ScheduleRecommend` 负责 AI 推荐。
- `OnboardingGuide` 负责家庭画像和初始推荐。
- `Tasks` / `PublishTask` 负责任务执行。
- `Rewards` 负责积分兑换。

这些功能方向一致，但数据结构还没有统一。后续要把产品推进成“家庭 AI 管家”，必须先把主闭环统一成一个领域模型。

## 2. 主业务闭环

家庭画像 -> AI/模板生成日程 -> 家长确认 -> 日程拆任务 -> 孩子执行 -> 家长审核/自动确认 -> 积分奖励 -> 愿望兑换 -> 周期复盘 -> 优化下一轮日程

这个闭环是产品主线。其他功能应围绕它生长。

## 3. 核心对象

### FamilyAccount

家庭主账号。一个登录账号代表一个家庭空间。

主账号可以用手机号、邮箱或第三方登录创建。爸爸或妈妈只需要注册一次，其他家庭成员不需要再申请独立互联网账号。

核心原则：

- 一个主账号绑定一个家庭空间。
- 主账号负责云端登录、数据同步、账单、隐私授权。
- 家庭成员只是在家庭空间内切换身份。

### FamilyMemberIdentity

家庭内成员身份。包括爸爸、妈妈、孩子、老人等。

成员可以通过 PIN 或独立密码切换，不等同于 Supabase/Clerk/Auth 用户。

核心原则：

- 成员身份用于家庭内部权限和操作归属。
- 孩子不需要手机号或邮箱。
- 家长成员可以设置为管理员。
- PIN 只用于家庭内部切换，不应作为互联网登录凭证。

推荐权限模型：

- `owner`：家庭主账号拥有者。
- `admin`：家庭管理员，可管理成员、日程、奖励和审核。
- `parent`：家长，可创建任务、审核、管理奖励。
- `child`：孩子，可查看和完成任务、申请兑换奖励。
- `viewer`：只读成员，如老人或临时照看者。

### FamilyPlanningProfile

家庭画像。用于描述家庭整体情况，是 AI 规划的主要输入。

关键字段：

- 家庭所在城市、时区。
- 孩子列表。
- 家长工作时间和可陪伴状态。
- 每月预算。
- 教育目标。
- 特殊约束。

### ChildPlanningProfile

孩子画像。用于描述每个孩子的年龄、年级、兴趣、短板、性格和健康注意事项。

关键字段：

- 年龄、年级、性别。
- 强项和短板。
- 兴趣爱好。
- 性格特点。
- 作业时长。
- 屏幕时间规则。
- 健康备注。

### FamilySchedulePlan

家庭日程方案。它可以来自 AI、模板、社区或手动创建。

关键字段：

- 类型：作息型、周期型、目标型、容器型。
- 场景：工作日、周末、假期、寒暑假、旅行、医疗等。
- 来源：AI、模板、社区、手动。
- 时间范围。
- 日程时段列表。
- 家长提示。
- AI 假设。

#### 计划类型定义

计划不是简单的“任务集合”。它可以是一个时间段、一种周期安排，也可以是一件有明确结果的事情，还可以作为容器套住多个子计划。

- 作息型计划：工作日作息、周末作息、寒暑假日常安排。重点是时间结构和执行参考，不强行使用“计划进度”。
- 周期型计划：每周练琴、每周游泳、假期一周三次训练。重点是频率、持续性和阶段调整。
- 目标型计划：钢琴考级、完成一本书、比赛备考、某科提升。重点是里程碑、验收标准和结果进度。
- 容器型计划：学期总计划、暑假总计划，可以包含作息型、周期型、目标型子计划。

当前 UI 中的百分比应理解为“任务完成情况”。只有目标型计划才应进一步升级为真正的“目标进度/里程碑进度”。

复盘周期不应要求用户在创建计划时配置。系统应自动按周、月、学期、年度生成家庭复盘，统一盘点所有计划：

- 本周期完成了多少普通任务。
- 完成了多少次好习惯。
- 触发了多少次惩罚/扣星项。
- 各计划分别贡献了哪些完成项。
- 本周期获得和扣除了多少星星。

复盘的表达方式不应像管理后台报表，而应像家庭智能管家的鼓励性回顾：

- 先肯定孩子和家庭已经完成的小进步。
- 把星星、任务、习惯转成孩子能理解的正向反馈。
- 对扣星或坏习惯只做温和提醒，避免把报告变成批评清单。
- 自动预告下一周、下个月的重要事项，帮助家长提前准备。
- 不要求用户设置复盘频率、统计维度和展示参数。

### ScheduleSlot

日程中的一个时段，例如“17:30-18:30 作业时间”。

关键字段：

- 标题。
- 开始和结束时间。
- 分类：学习、生活、运动、兴趣、家庭、休息、医疗、旅行等。
- 适用孩子。
- 是否需要家长参与。
- 建议奖励星星。

### TaskDraftFromSchedule

从日程拆出来的任务草稿。它是日程和现有 `Task` 系统之间的桥。

## 4. 代码基准

新的领域模型落在：

`src/domain/familyPlanning.ts`

它暂时不替换现有页面，而是作为后续迁移和新功能开发的统一基准。

后续新增 AI 日程、社区模板、一键改编、寒暑假规划时，应优先对齐这些类型。

## 5. 推荐迁移顺序

### 第一步：保留现有页面，统一新功能输入输出

新建的 AI 日程规划、家庭画像、社区模板，先使用 `FamilyPlanningProfile` 和 `FamilySchedulePlan`。

### 第二步：把 AI 推荐结果转成标准日程

把 `ScheduleRecommend` 当前的 `ScheduleRecommendation` 转换成 `FamilySchedulePlan`。

### 第三步：把计划向导输出转成标准日程

把 `PlanWizard` 的 `DailyScheduleTemplate` 转换成 `FamilySchedulePlan`。

### 第四步：一键拆任务

使用 `schedulePlanToTaskDrafts()` 把日程时段拆成任务草稿，再交给现有 `addTask()`。

### 第五步：复盘闭环

任务完成数据反哺 `FamilySchedulePlan`，生成周报、月报和下一轮优化建议。

### 第六步：AI 四象限权衡

四象限不是让用户手动维护优先级的工具，而是让 AI 帮家庭做取舍：

- 支持今日、本周、本月三个核心视角。
- 自动判断任务的紧急度和重要度。
- 对家长输出“先做什么、什么可以顺延、什么可以减少”。
- 对孩子输出鼓励式说明，帮助孩子理解为什么先完成这些事。
- 当任务过多时，系统应主动建议减法，避免把所有事项都推给家庭。

### 第七步：心愿兑现闭环

孩子用积分兑换的很多内容，本质上不是商品，而是家庭承诺。例如周末游玩、暑假旅行、父母陪伴、一次特权或一个愿望。

系统应在家长确认兑换后，自动生成父母侧的“兑现心愿”任务：

- 任务分配给父母或家庭管理员。
- 标明是哪位孩子兑换、消耗了多少星星、心愿内容是什么。
- 保留原始心愿 ID，避免重复生成兑现任务。
- 进入父母的日程/任务/四象限中，提醒家长完成承诺。
- 系统应自动给出轻量兑现时间：周末类心愿提醒到下一个周末，寒暑假类心愿提醒到对应假期内，普通心愿默认给父母一个合理兑现窗口。
- 周报、月报、学期报中应单独展示已经兑现的心愿，让孩子看到“努力 -> 积分 -> 愿望 -> 父母兑现”的完整正反馈。
- 表达上强调“兑现约定”，而不是把孩子的愿望变成家长的负担。

## 6. 当前阶段的边界

本阶段只建立模型，不大改页面，不改变数据库，不触碰多端同步。

原因：

- 当前项目刚恢复类型检查通过，应该避免立即做大面积重构。
- 先让后续新增功能有统一基准。
- 等主模型稳定后，再逐步迁移页面和数据库。
