# 离线优先执行方案

更新时间：2026-05-13

## 1. 产品原则

星愿卡的家庭数据、日程安排、任务、积分和奖励必须满足：

- 离线时能正常查看和操作。
- 在线时自动同步到云端。
- 多设备最终保持一致。
- 家长和孩子不需要理解网络状态，也不应该因为断网丢失操作。

家庭日程产品的网络环境天然不稳定：学校门口、地铁、旅行、医院、地下停车场都可能断网。因此本项目应采用“离线优先，本地立即生效，云端最终一致”的策略。

## 2. 目标体验

### 离线状态

- 可以查看家庭成员、日程、任务、奖励和历史记录。
- 可以创建任务、完成任务、生成日程、兑换奖励。
- 页面立即更新。
- 顶部或设置页显示“待同步 N 项”。
- 不阻断用户操作。

### 恢复联网

- 自动上传离线期间的操作。
- 自动拉取其他设备的更新。
- 同步成功后提示轻量状态。
- 如果冲突，尽量自动解决；高风险冲突交给家长确认。

## 3. 技术原则

### 一个主账号，一个家庭空间

当前产品应采用：

**一个登录账号 = 一个家庭账户。**

家庭成员通过 PIN 或独立密码在家庭空间内切换身份，而不是每个成员都注册一个互联网账号。

这对离线同步非常有利：

- 登录一次即可缓存整个家庭空间。
- 离线时只需要切换当前家庭成员，不需要切换云端登录态。
- 所有操作进入同一个家庭同步队列。
- 避免爸爸、妈妈、孩子多个云端账号同时写同一份家庭数据带来的冲突。

同步队列的归属应以 `familyId` 为主，以 `actorMemberId` 标记家庭内部操作者。

### 读本地

页面读取优先从本地缓存读取，而不是每次都请求 Supabase。

原因：

- 速度快。
- 离线可用。
- 减少移动端网络问题。

### 写本地，再排队同步

所有写操作先写入本地缓存，然后加入同步队列。

流程：

1. 生成本地 ID。
2. 写入本地缓存。
3. 立即更新 UI。
4. 加入 `sync_queue`。
5. 如果在线，后台上传。
6. 如果离线，等待联网后上传。

### 云端作为可信备份与多端同步中心

Supabase 不再是用户操作的第一阻塞点，而是同步中心。

## 4. 当前项目现状

项目里已经有以下离线相关模块：

- `src/lib/DataLayer.ts`
- `src/lib/SyncEngine.ts`
- `src/lib/StorageAdapter.ts`
- `src/lib/NetworkMonitor.ts`

这些模块方向正确，但主应用目前仍大量依赖：

- `FamilyContext`
- `src/lib/api.ts`
- 直接 Supabase 查询

也就是说，当前状态是：

**离线基础设施已经存在，但主业务闭环还没有完全迁移到离线优先数据层。**

## 5. 风险评估

### 高风险：直接写 Supabase

如果网络失败，操作可能失败或用户感知不稳定。

影响场景：

- 创建任务。
- 一键生成任务。
- 完成任务。
- 审核任务。
- 兑换奖励。

### 高风险：积分和任务状态冲突

任务完成、家长审核、积分发放属于高价值操作，不能简单“最后写入覆盖”。

这类操作需要：

- 防重复发星。
- 操作幂等。
- 明确谁操作、何时操作、操作 ID。当前离线队列已开始记录 `actorMemberId`，后续应同步升级为服务端审计字段或 RPC 参数。
- 本地先维护一份最近操作审计缓存，供家长在离线状态查看关键变化。云端审计表上线后，再把本地审计同步为服务端记录。

### 中风险：localStorage 容量有限

Web 端当前本地存储主要基于 localStorage。短期够用，长期应迁移 IndexedDB。

### 中风险：多端字段不完全统一

Web、Capacitor、小程序要共享同一数据契约，否则同步会出现字段丢失。

## 6. 推荐架构

```
页面/组件
  ↓
FamilyContext
  ↓
DataLayer
  ↓
本地缓存 + 离线操作队列
  ↓
SyncEngine
  ↓
Supabase
```

身份模型：

```
Auth Account
  ↓
Family
  ↓
Members
  ↓
currentMember
```

`Auth Account` 负责登录和云端同步，`currentMember` 负责当前操作身份。

短期不建议让页面直接调用 `DataLayer`，而是让 `FamilyContext` 成为过渡层：

- 页面继续使用 `useFamily()`。
- `FamilyContext` 内部逐步改为调用 `DataLayer`。
- 这样页面改动小，风险低。

## 7. 数据同步策略

### 低风险数据：最后写入优先

适用：

- 任务标题。
- 任务描述。
- 图标。
- 奖励描述。
- 日程模板文本。

策略：

`updated_at` 新的覆盖旧的。

### 中风险数据：字段合并

适用：

- 任务状态。
- 打卡次数。
- 成员星星数展示值。

策略：

- 任务状态只向前推进：`pending -> reviewing -> completed`。
- 打卡次数取较大值。
- 星星展示值从交易流水重新计算，不长期依赖客户端覆盖。

### 高风险数据：事件化

适用：

- 完成任务。
- 审核任务。
- 发放积分。
- 兑换奖励。

策略：

不要只保存最终状态，要保存操作事件：

- `task_completed`
- `task_approved`
- `stars_earned`
- `reward_redeemed`

每个事件有唯一 `operationId`，重复同步时服务端应识别并跳过。

## 8. MVP 落地顺序

### 第一步：先迁移任务读写

目标：

- 创建任务离线可用。
- 完成任务离线可用。
- 一键生成任务离线可用。
- 恢复联网后同步。

动作：

- 给 `DataLayer` 补齐 `planId` 字段。
- 让 `FamilyContext.addTask()` 先走 `DataLayer.addTask()`。
- 初始化时从 `DataLayer.getTasks()` 加载本地任务。

### 第二步：迁移成员和奖励

目标：

- 家庭成员、奖励商城离线可查看。
- 新增奖励和兑换奖励可排队同步。

动作：

- `members`、`rewards` 走本地缓存。
- 兑换奖励改成事件化操作。

### 第三步：迁移积分流水

目标：

- 星星变化可追溯。
- 防重复发放。

动作：

- 所有星星变动写 `star_transactions`。
- 本地先生成交易记录。
- 云端同步成功后做 ID 映射。

### 第四步：增加同步状态 UI

目标：

- 家长知道数据是否已保存。
- 但不要打扰用户。

展示：

- 已同步。
- 离线可用。
- 待同步 N 项。
- 同步失败，点击重试。

### 第五步：升级本地存储

短期使用 localStorage。

中期升级 IndexedDB：

- 更大容量。
- 更适合日程、社区模板、图片缓存。
- 更适合同步队列。

## 9. 对当前主闭环的具体影响

### 家庭画像

必须本地保存。用户填写一半断网或退出，也不能丢。

家庭画像属于家庭空间，不属于某个单独成员。

### AI 日程

AI 生成需要联网，但生成后的方案必须本地保存。

离线时：

- 可以查看历史生成方案。
- 可以编辑已有方案。
- 可以用内置模板生成日程。

### 日程转任务

必须离线可用。

因为模板和已生成日程都在本地，拆任务不依赖网络。

### 任务执行

孩子点击完成任务必须离线可用。

联网后同步给家长端。

### 家长审核和积分

可以离线操作，但必须事件化，避免重复发星。

事件必须记录 `memberId`，用于知道是爸爸、妈妈还是孩子触发了操作。

## 10. 下一步工程动作

建议下一步直接做：

1. 给 `DataLayer.DataTask` 增加 `planId`。
2. 修复 `SyncEngine` 中明显的清理函数拼写问题。
3. 给 `DataLayer` 增加从云端任务到本地任务的映射测试。
4. 让 `PlanDetail` 的一键生成任务优先通过 `DataLayer` 路径，或者先让 `FamilyContext.addTask()` 内部切到 DataLayer。

推荐优先选择第 4 条的保守版本：

**保持页面不变，只改 `FamilyContext.addTask()` 的内部实现，让它逐步使用 DataLayer。**

这样不会大面积改 UI，也能让主链路开始具备离线能力。
